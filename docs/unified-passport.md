# Unified Passport client contract (a16 candidate)

This client shows one Passport while keeping Personal and Business as separate `passport-vault-v1` envelopes. The host stores only the existing ciphertext, scope, and storage metadata. There is no vault migration or shared raw key.

## Dedicated origin

Serve the static client from a dedicated HTTPS origin separate from the application host. It needs `allow-scripts allow-same-origin` in the iframe to use IndexedDB; that combination must never be used when the iframe and parent have the same origin. The deployed `client-policy.mjs` must export a reviewed, exact HTTPS `ALLOWED_PARENT_ORIGINS` list. The packaged list is empty. The dedicated client refuses to run with an empty list. The host must pin the exact child origin and window source, send to an exact target origin, and supply a new nonce and capability for every mounted frame. A dedicated static host should block third-party scripts and restrict `frame-ancestors` to the application origin. It should carry no application session cookie.

`hosted.html?view=questions` loads only the questions client. It accepts either the signed proposal batch channel or the signed single deal-step question channel; the first valid context determines the fixed question surface and release shape. `hosted.html` loads the book client. No URL value or parent message selects an arbitrary module. The questions view sends `view-ready` after its signed context has rendered; the application can keep its existing question form until that signal. `open-book` asks the application to open its Passport setup surface; it includes no draft or key. The parent may send fixed `open-panel` (`information`, `goals`, `sharing`) and `lock-all` controls on the storage channel. All these messages require the same pinned source, origin, nonce, and capability. `lock-all` clears unlocked books and persists a local lock marker; the device only resumes after the owner's explicit Unlock action. A lock also invalidates an in-flight load, decrypt, or recovery operation so a late result cannot reopen a book.
The questions client also reports `connection-state` with one boolean for whether every needed book is currently unlocked. The host should replace native question controls only after both `view-ready` and `connected:true`; a later `connected:false` restores its ordinary controls without receiving any private values. Lock and Forget send only a `lock` signal through an owner-bound, same-origin BroadcastChannel. Other active Passport frames clear keys, visible answers, suggestions and file references without any plaintext or unlock message crossing the channel.

Dedicated storage init adds `storageIdentity:{ownerBinding,parentOrigin}` to `passport-hosted-v1`. `ownerBinding` is a stable opaque server-derived account binding; it is never treated as authentication. The child independently checks `event.origin` against `client-policy.mjs` and requires `parentOrigin` to match. The host supplies the existing `load/save/delete` ciphertext protocol unchanged. No key, recovery file, answer candidate, or unselected draft may cross it.

## Remember this device

Remember is opt-in after each book has been opened with its own recovery file. The isolated origin stores a nonextractable AES-GCM wrapping `CryptoKey` in IndexedDB and wraps each existing vault key separately. Authenticated additional data binds the wrapper to parent origin, opaque owner binding, scope, and vault ID. The raw vault key is exported only inside the isolated client while wrapping; it is never placed in localStorage, sent to the host, or stored unwrapped in IndexedDB. Forget serializes against an in-flight Remember and deletes the local key and wrappers for that binding. A lost or evicted IndexedDB store requires the corresponding recovery file again. Nonextractable does not protect against malicious code running in the isolated origin or a compromised device; storage may be cleared by browser policy, especially on Safari/iPhone. Do not promise permanent silent unlock.

## Questions and disclosure

Signed question context can add `bookSubjects:{personal,business}` using each book's existing subject and per-question `bookScope` defaults. The user can change the Personal/Business choice on each row. A changed choice reads and saves only that book and its subject; nothing is copied across books. Canonically tagged suggestions use the existing request type, entity, context key, format, and option set even if question wording differs. Untagged suggestions require exact normalized wording, subject, format, and options. Suggestions sit below the field and require **Use answer**. Only empty untouched duplicates with the same canonical identity and book receive automatic typed-value propagation. An edited or conflicting answer is never overwritten.
Older library answers saved as `fields.answer` remain eligible for untagged exact-text suggestions. They cannot satisfy a signed choice question because those answers lack a recorded option set. A removed topic also removes legacy label-based suggestions; only exact question wording may then match. Each suggestion names its saved source question and still requires **Use answer**.

Typing and blur update one private answer entry and its stable draft pointer in the same per-book CAS snapshot. The draft can reopen under a new signed request ID for the same task, question digest, format, options, subject and book. Exact classified answers with an explicitly chosen entity default to reusable; untagged answers remain task-bound. The question sheet has one compact connection line; Personal/Business and topic controls live in each row's optional tag details. Removing a topic affects only local classification, never the signed request. Forget remains in the book settings. A failed or ambiguous save blocks Send and retains the visible input. Review references the already-saved answer versions and saves a private approval record before release. The question release channel sends only the user's explicitly selected answers and files to the signed recipients. A lock or changed local vault revision invalidates the prepared release. The fixed client does not route full vaults through the host to make the sheet appear native.
